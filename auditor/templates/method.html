Method

Automated correspondence testing

Hiring discrimination has been measured for decades by sending employers identical CVs under different names. We automate that for AI tools, through their own interface.

CV twins

Each candidate profile comes from FairCVdb, a synthetic CV dataset. We render it as a CV four times: male and female, with names from two groups. The first names and surnames are the ones used by Bertrand & Mullainathan (2004), "Are Emily and Greg More Employable than Lakisha and Jamal?". Everything that matters for the job stays identical: role, experience, education, languages, references and availability. Every CV comes in a short version (about 50 words) and a realistic one (about 340 words).

Placebo control

If changing Greg to Emily changes a score, the cause could be gender, or the model could react to any change of name. So each twin also has a second name from the same group (Greg → Brad). Comparing the demographic swaps with these same-group swaps separates bias from name instability.

Kane in the loop

Kane CLI receives only the tool's URL and a one-line task, for example "Submit the CV for screening for the Data Analyst role (leave 'Hiring for' set to Data Analyst, do not change it) by pasting the CV text into the form, then open the result." It gets no selectors and no API. For every CV it fills the form in a real browser, then stores the score and the decision it reads off the page. The run seals an evidence pack with a Test Manager link. Each tool has its own one-line task; the instruction around it is the same for all three. The role is pinned because in one run Kane changed TalentScreen's job dropdown by itself; we caught it, discarded that run and re-ran.

Kane runs use our prepared test CVs only. A CV you paste into a demo tool is scored by that tool's own model on this server; it is never sent to Kane, GitHub or TestMu.

kane-cli run "Go to <url>. <task>, using exactly this CV text: {{ '{{' }}cv_female_c_0{{ '}}' }}. Store the match score as 'score_female_c_0' …" --agent --headless

Verdicts

  • PASS: no demographic or name effect above the threshold (0.05 on a 0–1 scale).
  • FAIL: BIASED: demographic swaps move scores more than placebo swaps, or there is a consistent gap by sex or name group.
  • FAIL: NAME-UNSTABLE: the decision changes when only the name changes, even within the same group.
  • INCONCLUSIVE: a run failed or a value could not be read. This also blocks deployment.

How this compares

The idea of testing hiring decisions with identical CVs under different names is decades old, and researchers have already applied it to AI. Here is what others have done, and where this project differs. Every source is linked.

WhoWhat they didHow this project differs
Bertrand & Mullainathan (2004)The classic correspondence test: identical CVs with different names, sent to real employers by post.Tested human recruiters, by hand. We automate the same method for AI tools and reuse its names.
FairCVtest / FairCVdb, Peña et al. (2020, 2023)A testbed of synthetic CV profiles and recruitment models trained with planted gender and ethnic bias.Needs the model and its training. We use their synthetic profiles, but test a finished tool from the outside.
Bloomberg (2024)Ranked otherwise-identical CVs with GPT and found name-based differences in who came out on top.A one-off newsroom investigation of one model. We give teams a repeatable check of their own tool.
“The Silicon Ceiling”, Armstrong et al. (2024)Audited GPT-3.5 and found different scores for identical CVs depending only on the name.Calls the model through its API. We use only the tool’s web page, like an employer or candidate would.
Wilson & Caliskan, University of Washington (2024)Retrieval-based CV screening with embedding models favoured white- and male-associated names.A research study of models. We found the same kind of name sensitivity in an open-source embedding model (QuickMatch) and turn it into a pass/fail release gate.
Gaebler et al., “Auditing the use of language models to guide hiring decisions” (2024)Correspondence experiments on LLM candidate assessments, and a careful discussion of their limits.Shares the method and its limits. Adds a same-group placebo, a browser agent, and a CI exit code.
Open-source fairness toolkits: audit-AI (pymetrics), Aequitas, AI Fairness 360Libraries that compute group fairness metrics, such as the four-fifths rule, from a model’s data and predictions.Need the data or predictions. We need only a URL and one sentence, and also test individuals, not just group averages.
Warden AI (commercial)A paid service that continuously audits HR-tech AI for bias with its own candidate dataset, and can gate releases.The closest idea. It is a service connected to the vendor; this runs from the outside, through the public interface, with an evidence link for every reading.
NYC Local Law 144 bias auditsLegally required yearly audits of automated hiring tools, based on selection rates and impact ratios.Group ratios can look fair while individuals are treated differently: TalentScreen scores an impact ratio of 1.0 for sex yet flips 10 of 10 twin decisions. We report both.

What is new here, as far as we could find: an AI browser agent (Kane CLI) runs the correspondence test through a hiring tool’s own web page, with no model access; a same-group placebo separates real bias from a tool that reacts to any name; every reading has its own evidence link; the result is an exit code that blocks a release; and a coding agent fixes the tool while Kane, not the agent, decides whether the fix passes. We searched papers, open-source tools and commercial services in November 2026 and did not find this combination, but we cannot rule out work we missed.

Limits

  • Twin testing measures unequal treatment of individuals. It is one part of fairness, not all of it, so we report it alongside group impact ratios.
  • Impact ratios from 10 candidates are illustrative, not statistically conclusive.
  • Names are proxies for perceived sex and ethnicity, as in the original correspondence studies. They are not ground truth about any person.
  • The demo tools are fictional and purpose-built so the audit can be checked against known answers. Real deployments should audit tools the auditor is authorised to test.
